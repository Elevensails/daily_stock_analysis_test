# PRD — U3 修改策略（引导式修复 + 安全降级发布）

> **项目信息**
> - Language: 中文
> - Programming Language: Python（GitHub Actions 工作流 + DeepSeek 生成报告），前端为静态站（`dsa-test/web/`，Vite/HTML+CSS）
> - Project Name: `u3_guided_repair_safe_degrade`
> - 原始需求复述: 用户原话「后续必须要解决幻觉，而不是只报然后 reject」；后续确认「如果报告全都 reject，那没有实际意义了，建议加入修改的策略」。即把"修不好就空 reject"升级为"修不好也给减置信版"，并在 repair 过程中引入**引导式定向修复**以降低再引入幻觉概率。

---

## TL;DR

- U3 gate 已真实拦截 2 份幻觉，但纯 `reject` 对终端用户**零交付**，用户要求"解决幻觉而非只报"。
- 本 PRD 把闭环升级为 **引导式定向修复 + 安全降级发布**：修不好也给"减置信版"，且修复时只改违规段、回传最新原因。
- 范围已拍板（引导式修复 + 安全降级发布），本文件交付产品目标 / 用户故事 / P0-P2 需求池 / UI 设计稿 / 待确认问题，不改任何代码。

---

## 1. 产品目标

**一句话**：将 U3 防幻觉闭环从"修不好就空 reject"升级为"引导式定向修复 + 安全降级发布"，在守住质量底线的前提下保证终端用户始终有报告可读。

**背景**：U3 validator gate 上线后已**真实拦截 2 份幻觉**（涨停写反、红线=具体买入建议等），手动 Run 两份已知幻觉报告被正确拦截、重写 1 轮仍 reject —— 这是安全降级的正确行为，但**纯 reject 对终端用户无任何交付物**，违背了"为用户提供 A股 报告"的核心价值。用户明确要求"后续必须要解决幻觉，而不是只报然后 reject"。因此本期目标有二：

1. **引导式修复（降再幻觉概率）**：repair loop 从"整篇重写"改为"只改 validator 标出的违规段、保留其余"，并回传**最新一轮**校验原因，让模型看到上一轮还差什么，避免全文重写引入新幻觉；轮数由 1 放宽到 2–3，温度真正透传。
2. **安全降级发布（保底交付）**：repair 仍超限/失败不再空 reject，而是剥离被标红的违规段（红线/矛盾/未举证断言）、保留合规主体，发布**减置信版**，并在前端与终态日志中明确标注"需人工复核"。

## 2. 用户故事

- **作为 A股报告读者**，当某篇报告的个别片段触发合规红线时，我希望仍能看到一份标注"需人工复核"的减置信版，而不是空白页，以便我仍能获取主体行情与量化结论。
- **作为 rewrite 修复模型**，我希望在第 N 轮拿到**最新一轮**的校验原因和具体违规段指针，以便我只改被标红的部分、不重新生成全文，从而降低引入新幻觉的概率。
- **作为系统运营**，我希望在 `logs/judge_rejects.jsonl` 中能通过 `final_action` 字段区分 `reject`（彻底失败）与 `emit_degraded`（安全降级发布），以便统计拦截率、降级率并配置告警。
- **作为报告读者**，我希望减置信版在报告头部清晰标出降级范围与置信度降档，以便我判断是否采信其中的结论。
- **作为值班工程**，我希望 repair 轮数可在 2–3 之间配置、且只有超限才走降级分支，以便在时效与质量之间权衡、避免在余量充足时过早放弃修复。

## 3. 需求池

> 优先级：P0 = 必须（Must），P1 = 应当（Should），P2 = 可选/后续（Could）。

### P0（必须）

| 编号 | 需求 | 说明 / 验收要点 |
|---|---|---|
| P0-1 | **结构化违规段输出** | `validator.py` 的 gate 结果在现有 `reasons` 文本基础上，**结构化输出违规段定位（segment 指针）**（如段落/句子/行索引 + 违规类型），供 repair 定向改段。 |
| P0-2 | **定向改段** | `repair.py` 的 `repair_report` 由"整篇重新生成"改为"只改 validator 标出的 `violation_segments`，保留未标红内容"；`prompts_repair.py` 指令同步改为"按 `violation_segments` 定向修订，保留未标红内容"。 |
| P0-3 | **回传最新原因** | repair loop 每轮回传**最新一轮**的校验原因（而非仅首轮），使模型感知"上一轮还差什么"。 |
| P0-4 | **safe_degrade 分支** | repair 仍超限/失败 → **不再空 reject**：剥离被 validator 标红的段（红线 / 矛盾 / 未举证断言），保留合规主体，组装发布**减置信版**。 |
| P0-5 | **emit_degraded 终态** | `logs/judge_rejects.jsonl` 的 `final_action` 新增枚举 `emit_degraded`，与既有 `reject` / `emit` 区分；记录 `repair_rounds`、降级段清单。 |
| P0-6 | **降级徽标（前端）** | `scripts/emit_frontend_artifacts.py` 识别 `final_action=emit_degraded` → 正常 emit，并渲染前端"⚠️ 部分内容经安全降级，需人工复核"徽标（样式见 §4）。 |
| P0-7 | **config 开关** | `src/config.py` 新增/启用 `safe_degrade_enabled`（**默认 True**），作为降级分支总开关，便于紧急回退到 reject-only。 |

### P1（应当）

| 编号 | 需求 | 说明 / 验收要点 |
|---|---|---|
| P1-1 | **REPAIR_TEMPERATURE 真正透传** | `src/analyzer.py` 的 `call_rewrite_llm` 真正透传 `REPAIR_TEMPERATURE`（当前为**非阻塞遗留、未透传**），定向改段调用使用该温度。 |
| P1-2 | **轮数 2–3 可调** | `REPAIR_MAX_ROUNDS` 由 1 提到 **2–3**；`config.py` 对其 clamp 上限提到 3，默认建议在 2–3，可经 workflow 余量（已放宽到 30min）运行。 |

### P2（可选 / 后续）

| 编号 | 需求 | 说明 |
|---|---|---|
| P2-1 | **段级 patch 合并更细粒度** | `call_rewrite_llm` 支持"段级 patch"合并（仅替换违规句而非整段），进一步降低改动面。 |
| P2-2 | **降级置信度分级展示** | 按"剥离段 / 保留段"比例给出多档置信标识（如高/中/低），而非统一"减置信版"。 |

## 4. UI 设计稿（降级报告前端展示）

**适用页面**：`dsa-test/web/` 静态站，当某次报告 `final_action == "emit_degraded"` 时渲染。

### 4.1 展示位置与视觉权重

- **报告正文页顶部横幅（最高权重）**：标题下方、正文上方全宽 banner。琥珀黄底（`#FEF3C7`）+ 深褐字（`#92400E`），左侧 ⚠️ 图标，文案「⚠️ 部分内容经安全降级，需人工复核」，右侧放置信度降档标识（如「置信度：中」或「减置信版」）。
  - *视觉原则*：醒目但不惊悚 —— 用**琥珀/橙**系警示色，**禁用**刺眼纯红、禁用闪烁动画，仅作"请留意"提醒，不制造恐慌。
- **被剥离段占位**：原红线段位置展示低调占位条「【本段因触发合规红线已安全降级移除】」，避免页面出现空洞、同时明确"此处有内容被移除"。
- **归档/列表页卡片角标**：报告封面缩略图右上角加小型徽章「已降级」，便于在索引页快速识别哪些报告是减置信版。

### 4.2 ASCII 示意（报告正文页）

```
┌──────────────────────────────────────────────────────────┐
│  📈 2025-07-31 A股 大盘复盘 · 减置信版                       │
├──────────────────────────────────────────────────────────┤

├──────────────────────────────────────────────────────────┤

│  今日沪指收 3,xx.xx，量能较昨日 …（合规主体，正常展示）          │
│                                                                 │
│  ┌─【本段因触发合规红线已安全降级移除】──────────────┐         │  ← 占位条
│  └──────────────────────────────────────────────┘         │
│                                                                 │
│  二、板块轮动 …（合规主体，正常展示）                            │
└──────────────────────────────────────────────────────────┘
```

### 4.3 归档/列表页卡片

```
┌───────────────┐
│ [已降级]  🔻   │   ← 右上角小徽章
│  个股报告 07-31 │
│  置信度：中     │
└───────────────┘
```

## 5. 待确认问题（需用户 / 架构师拍板）

1. **发布流程**：减置信版是否仍走**正常 emit 发布流程**（PRD 倾向"是，正常 emit + 前端徽标"），还是单独存档不进主站？关系到 `scripts/emit_frontend_artifacts.py` 的分支逻辑。
2. **徽标覆盖范围**：降级徽标是否**仅在报告正文页**展示，还是**归档/列表/索引页也要展示**？影响 web 多处渲染点（P0-6 默认正文页 + 列表角标，需确认）。
3. **段级定位精度**：`validator.py` 的 segment 指针需要精确到**段落 / 句子 / 行**？精度越高 repair 改动面越小、再幻觉风险越低，但实现成本越高（影响 P0-1 与 P2-1）。
4. **被移除段可见性**：降级后是展示**"已移除"占位条**，还是**完全隐去**被标红内容？占位更透明但页面更长。
5. **运营告警**：`emit_degraded` 是否需要在 jsonl 留痕之外触发**额外告警**（飞书 / 邮件 / Issue）？还是本期仅留痕、告警后续做？
6. **置信度展示粒度**：统一"减置信版"标识（P0），还是按剥离比例做**分级展示**（P2-2）？决定 P2 是否提前纳入本期。
7. **降级开关回退**：`safe_degrade_enabled` 默认 True；若需紧急回退到 reject-only，是否要求**零代码、仅改 config**即可生效（PRD 倾向是）？

## 6. 验收标准（验证预期）

- **单测**：扩展 `tests/test_repair_loop.py`，覆盖——定向改段、safe_degrade 分支、终态枚举（`reject` / `emit_degraded` / `emit`）。
- **实锤（手动 Run）**：以一份已知幻觉报告手动 Run（`time_slot=0915`），确认：
  - `logs/judge_rejects.jsonl` 中 `repair_rounds` 较旧版提升（>1）；
  - `final_action` 出现 `emit_degraded`；
  - 前端页面可见"需人工复核"徽标与降级占位条。
- **回归**：U3 judge + repair 现有 **19/19** 单测不回退。
